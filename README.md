# Agent Lab

一个本地启动的桌面 App，用来学习和拆解 AI agent 的工作原理。
它不重写 Codex，而是把 `codex app-server` 当作 agent 内核，自己只做界面。

> **第一次用？看 [QUICKSTART.md](QUICKSTART.md)**——五分钟上手：启动、配模型、
> 选项目、干活、验证。本 README 是完整的探索记录（约 2000 行），适合想搞懂
> 「为什么」的时候按需查阅。

## 启动

双击 `启动 Agent Lab.bat`，会打开一个独立的桌面窗口（无地址栏）。

这个入口是静默的（不弹黑框），日志写到同目录的 `launch.log`，启动失败先看它。
它做了三件克制的小事，都是实测过的（实验 15）：

- **连点两次不会起第二份服务**：先问一下端口上有没有人在，有就只开窗口。
- **关掉窗口服务就退**：桌面模式没人连了会自动退出；留 15 秒宽限给浏览器刷新。
- **调试不受影响**：直接 `node app/server.mjs` 时不会自动退出，方便挂调试器。
也可以在终端运行：

```bash
node start.mjs
```

### macOS 也能跑

双击 `启动 Agent Lab.command`（macOS 认这个后缀），或者终端里 `node start.mjs`。

第一次用要赋一次执行权限：

```bash
chmod +x "启动 Agent Lab.command"
```

`node start.mjs` 在两个系统上是同一条命令。差别只在细节，都自动处理了：

- **窗口**：Windows 找 Edge/Chrome，macOS 找 `/Applications` 下的 Chrome / Edge / Brave / Chromium。
  都走 `--app=` 那个「像原生窗口、没有地址栏」的模式。找不到就退化成打印网址。
- **内核**：自编译内核的路径两边不同（Windows 那个 target 目录多一层 `.exe`），
  没有就回退到 PATH 里的 `codex`。想强制指定：`CODEX_BIN=/path/to/codex`。
- **知识库**：按 `~/Documents/Codex/CodexMemoryVault` 找，不再写死某个盘符。
- **指定浏览器**：`AGENT_LAB_BROWSER="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"`。

第一次在 Mac 上跑，需要先装依赖（只需要 Node）和内核：

```bash
brew install node
npm install -g @openai/codex      # 或者自己编译一份，再用 CODEX_BIN 指过去
node start.mjs
```

默认工作目录是 `agent-lab` 本身，可用环境变量覆盖：

```bash
AGENT_CWD="C:/你的项目" PORT=8787 node start.mjs
```

### 密钥怎么放（别写进配置）

这个项目原来把 API token 明文写在 `codex-home/config.toml` 里，那是不对的：**那个目录要进版本库，明文密钥一旦 commit 就等于公开**。内核自己也把 `experimental_bearer_token` 标成「不推荐，请用 `env_key`」。

现在的做法是分开：

```
codex-home/config.toml     env_key = "AGENT_LAB_API_KEY"   ← 只留一个变量名
源码运行：agent-lab/.env    AGENT_LAB_API_KEY=sk-...        ← 真值，被 .gitignore 排除
安装版：<用户数据目录>/.env  AGENT_LAB_API_KEY=sk-...        ← 真值，权限 600
```

`app/server.mjs` 启动内核时读 `.env`，把键值放进子进程环境。**环境变量优先**，所以临时覆盖直接 `AGENT_LAB_API_KEY=xxx node start.mjs` 就行。

安装版的可变数据不再写进 `Agent Lab.app`，默认落在：

```
macOS    ~/Library/Application Support/AgentLab
Windows  %APPDATA%\AgentLab
Linux    ~/.config/AgentLab
```

其中包含 `.env`、`agent-lab.settings.json`、`projects.json`、`codex-home/` 和运行用量缓存。首次启动新版会从旧包（或源码仓库）迁移一次已有配置；之后升级 App 不会覆盖这些文件。需要改位置时设置 `AGENT_LAB_DATA_DIR`。

新机器上从 `.env.example` 复制一份 `.env` 填自己的 token 即可。

顺带把 `.gitignore` 也补了——之前没有。除了 `.env`，还挡住 `codex-home/`（实测 1.9G，含会话记录）和 `.edge-profile/`（546M 浏览器 profile）。整个目录原本 2.4G，绝大部分是运行数据，不该跟着代码走。

这些都有自动检查兜底（实验 22）：会验证配置文件里不含明文密钥、`.gitignore` 挡住了该挡的、而且**真的能拿 `.env` 里的密钥跑通一轮**（没有认证错误才算过）。光看文件写对了不算——密钥真正的考验是链路通不通。

这个 App 用的是自己的 Codex 配置（`codex-home/`），不是你在 Codex 桌面版用的那份。
想让它继承全局 `~/.codex`，加一个环境变量就行：

```bash
AGENT_CODEX_HOME=global node start.mjs
```

### 换模型（以及一个很难发现的坑）

模型名写在 `codex-home/config.toml` 的 `model =` 那一行，改完重启 App 即可。
当前用的是 `xiaomi/mimo-v2.6-flash`（走本地中转 `127.0.0.1:57321`）。

换模型前建议先直接打一次中转确认它活着，别拿 App 去试：

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:57321/v1/models \
  -H "Authorization: Bearer $AGENT_LAB_API_KEY"
```

为什么强调这件事：中转上**有些模型名是坏的**，请求会返回 503 `auth_unavailable: no auth available`。
这个失败非常会骗人——它的表现不是报错弹窗，而是**整轮一句话都不回**。
界面上就是转圈转到你没耐心，实验里就是三条实验一起红。

实际踩到的例子（2026-09-22）：

| 模型 | 结果 |
| --- | --- |
| `cn:deepseek-v4.1-flash` | 503，上游错误 |
| `mimo-v2.6-flash`（不带前缀） | 400，unknown provider |
| `cn:hy4-preview` | 200，正常 |
| `xiaomi/mimo-v2.6-flash` | 200，正常（当前默认） |
| `xiaomi/mimo-v2.6-pro` | 200，正常 |

注意 `mimo-v2.6-flash` 和 `xiaomi/mimo-v2.6-flash` 是两个不同的东西：
少一个 `xiaomi/` 前缀，中转就认不出来。抄模型名的时候要把前缀带上。

**教训：模型不回复时，先确认模型本身活着，再去看 agent 逻辑。**
这次排查花了很久，就是因为一开始假设「是循环/工具坏了」，
实际上是第一圈请求就被中转拒了，后面根本来不及发生。

### 换模型还要补一条元数据（不然会静默降级）

光改 `model =` 还不够。内核靠一个「模型目录」文件知道每个模型的能力：
上下文窗口多大、支持不支持推理档位、能不能看图。这个文件是：

```
codex-home/model-catalogs/relay-mu96ubev.json
```

目录里**没有**你新写的模型名时，内核不会报错，只会发一句很不起眼的警告：

```
Model metadata for `xxx` not found. Defaulting to fallback metadata;
this can degrade performance and cause issues.
```

然后它拿一套**猜的**默认值继续跑。后果很隐蔽：上下文窗口按错的值算，
压缩可能在错误的位置触发；模型的能力也会被误判。

这次的例子：换到 `xiaomi/mimo-v2.6-flash` 后，实测全都能跑通，
但日志里一直带着那句 fallback 警告。补一条条目就好了——
照抄一个已知模型的条目、改掉 `slug` / `display_name` / `description` 三处，
剩下的能力字段先沿用（这个中转上的模型长得都差不多）。
补完重启，警告消失，实测 19 个实验全绿。

> 判断方法：跑任何一个实验，在输出里搜 `fallback metadata`。
> 搜到就说明模型目录该补了，即使这次实验是绿的。

这个坑还有一个批量版：中转的 `/v1/models` 会列出所有它能路由的模型，
但目录文件里只有当时加过的那些。实测（2026-09-23）：列表 27 个、目录 15 条，
差的 12 个里包括几个常用的。**所以换模型时，先把目录里有没有这个名字当第一步**，
没有就照上面方法补一条，再改 `model =`。

### 一份「别人也能跑起来」的检查清单

上面那些坑都是在本机跑起来的，而目标里有「Mac 上也能跑」。
这台机器是 Windows，真机没办法验；所以换了个能做的硬办法：**把所有写死的本机假设
找出来并改掉**，让代码不再依赖「我恰好在这台机器上」。下面每一条都是实际存在的写入点：

| 写死的东西 | 不修的话会怎样 | 改成什么 |
| --- | --- | --- |
| `python`（6 个脚本） | macOS 自 12 起不带 `python`，只有 `python3`，技能脚本全体跑不起来 | `lib/platform.mjs` 的 `findPython()` 逐个探活 |
| `USERPROFILE` 拼技能目录 | macOS 没这个变量，拼出一个奇怪的相对路径 | `os.homedir()` |
| 自编译内核路径（6 个脚本） | 两个系统产物路径不同，另一个直接用会 ENOENT | `findCodex()` 按平台拼 + 存在性检查 + 回退 PATH |
| `C:/Users/hero1157/.codex`（全局配置目录） | 换机器/换系统就错，而且只表现为「对比出来的数字不对」 | `os.homedir()` |
| `C:/Users/hero1157/Documents/...`（知识库） | 同上 | `os.homedir()` |
| 项目清单 `projects.json` 里写死盘符 | 列出一堆点开就报错的目录 | 列出前先 `existsSync` 过滤 |
| `start.mjs` 里另外又写了一份内核路径 | 同上（启动器自己起不来了） | 改成调用 `findCodex()` |

还有两条不是路径问题，但同样是「新机器上直接卡住」：

1. **`.env.example` 里那一行真值模板我补上了。**
   之前只有说明文字，没有 `AGENT_LAB_API_KEY=` 这行——照着它建 `.env` 会拿到一个空值，
   内核报 `Missing environment variable`。这种错在模板自己身上，不在用户身上。

2. **`codex-home/` 不能再被整个挡在版本库外。**
   这是最隐蔽的一条：那个目录里既有 1.9G 运行数据，也有真正的**配置**。
   全挡住的话，新机器 clone 下来目录是空的，内核**不报错**，只是静默退回默认配置——
   模型、密钥接入、工具挂载全丢。表现还是那句「模型一句话都不回」，
   跟之前那个坏模型的现象一模一样，排查会白跑很远。
   现在只放行 `config.toml` 和 `model-catalogs/`（共 1.4 MB），其余继续挡。

   > 写这条规则有个坑值得一提：**父目录被整个排除时，子文件的 `!` 否定规则会被忽略。**
   > 所以必须写 `codex-home/*` 而不是 `codex-home/`。两种写法在文本上都很像，
   > 只有真问一次 git 才知道哪个生效——实验 22 现在就是直接问 git 本人，
   > 不再自己扒 `.gitignore` 的文本。

> Mac 上还没做的：真机跑一遍。上面的改动只能保证「不再因为本机路径而断」；
> 窗口模式、沙箱行为、首次运行的完整流程，仍需要在 Mac 上实测一次才算数。
> 有个可复用的验证顺序：先 `node verify-install.mjs` 一键自检（它会指出缺什么，
> 比如 Python、密钥、模型元数据），修完 PASS 后再 `node start.mjs` 看窗口，
> 最后在 `projects.json` 里补上 Mac 侧的苍穹工程路径并跑 `node 26-cosmic-project.mjs`。

# 审批：agent 的安全闸门

## 为什么需要审批

模型能动手，就意味着模型可能做坏事——删文件、上传数据、跑危险命令。
所以生产级 agent 必须有一道闸门：**动手之前先问人。**

## 它是怎么工作的（这一点跟普通请求相反）

平时是「我发请求 → 服务端回响应」。
审批是**反过来**的：

```
客户端                          服务端（Codex）
   |                                 |
   |--- turn/start ----------------->|
   |                                 | 模型决定要写文件
   |<-- item/fileChange/requestApproval (带 id) ---|
   |                                 |
   |--- {id, result:{decision}} ---->|  ← 客户端必须用同一个 id 回话
   |                                 | 放行，继续执行
   |<-- turn/completed --------------|
```

关键点：**服务端主动发起的请求也带 `id`，客户端必须用同一个 id 回复。**
如果不回，这一轮就永远卡住——这正是最早版本 App 的死穴。

我踩过的坑：一开始把带 id 的消息全当成"响应"处理，
但 `pending` 表里没有这个 id，结果审批请求被**静默丢弃**，界面就一直转圈。

修法在 `server.mjs` 的 `onLine`：

```js
// 服务端主动发起的「请求」（审批等）：带 id + method，必须回话
if (msg.id !== undefined && msg.method) {
  serverRequests.set(String(msg.id), msg);
  broadcast({ id: msg.id, method: msg.method, params: msg.params, __isServerRequest: true });
  return;
}
```

## 决策有哪几种

命令执行（`CommandExecutionApprovalDecision`）：

| 决策 | 含义 |
|---|---|
| `accept` | 就这一次 |
| `acceptForSession` | 本会话后续同类都放行 |
| `decline` | 拒绝，但 agent 继续这一轮（它会想别的办法或报告失败） |
| `cancel` | 拒绝，并且立刻中断整轮 |

文件改动（`FileChangeApprovalDecision`）少了 `cancel`，也没有网络策略那两项。

注意 `decline` 和 `cancel` 的区别很重要：
**`decline` 是「这个不行，你换条路」，`cancel` 是「停下，别干了」。**

## 沙箱和审批是两个独立的旋钮

- **沙箱（`sandbox`）** 决定「物理上允许做什么」：`read-only` / `workspace-write` / `danger-full-access`
- **审批（`approvalPolicy`）** 决定「什么时候要问人」：`untrusted` / `on-request` / `never` / `granular`

我最早把 App 默认设成 `workspace-write` + 不处理审批，结果就是**碰到需要授权就卡死**。
现在默认改成 `read-only` + `on-request`：agent 想动任何东西都得先问你。
安全，而且能看清审批流程。

## 实测证据

用只读沙箱让它写文件，它必须请示：

```
[收到审批请求] id=0 类型=item/commandExecution/requestApproval
  命令="...powershell.exe" -Command "Set-Content -LiteralPath 'C:\新建文件夹\agent-lab\approval-test.txt' ...
  -> 已回复: accept  (200)

=== 审批次数 === 1
=== agent 最终回复 ===
已创建 approval-test.txt，内容为 `approved`，读取验证通过。

=== 结论 ===
[PASS] 审批链路通了：agent 请示 -> 我放行 -> 它继续干活
```

界面上的表现（截图见对话记录）：卡片显示
「需要你批准：修改文件」，三个按钮，点「允许一次」后变成
「已回复：accept」，agent 接着干活并完成。文件确实落了盘。

跑法：`node 05-approval.mjs`（需先 `node start.mjs`）。

# 我自己写的工具（MCP）

`mcp-my-knowledge/` 是一个零依赖的 MCP 服务，给 agent 两个能力：

- `knowledge_search` — 搜索我的个人开发知识
- `knowledge_add` — 把新知识追加进知识库

知识就存在 `mcp-my-knowledge/knowledge/index.md`，纯 Markdown，随时可以手改。

## 知识从哪来（现在已经接上真库）

最开始它只读仓库里一个 33 行的样例目录。现在已经接到真正的知识库
（`Documents/Codex/CodexMemoryVault`，几十个 Markdown、多层目录）。

接的时候碰到两个坑，都是真实问题：

1. **原来的检索器只扫顶层目录**。真库是 `20-项目/xx.md` 这种结构，
   不递归就会把大部分内容漏掉。改成递归收集，`.obsidian` 这类隐藏目录跳过。

2. **`-c` 的值是按 TOML 解析的，不是 JSON**。第一版写成 `{"KEY":"value"}`，
   冒号解析失败 → 整串被当成字符串 → 内核报 `invalid type: string, expected a map`。
   改成 TOML 内联表 `{ KEY = "value" }` 才行。

另外，**「读的库」和「写的地方」被刻意分开了**：

- 读：你真正的 Obsidian 库
- 写：仓库里的 `knowledge-inbox.md`

因为真库有自己的规矩（只记特定项目、不许混入杂事）。
让 agent 直接往里写，迟早会把库弄脏。现在它写的东西落在收件箱里，
你看过觉得合适再手动搬进去——**这一步的人工确认是故意留的**。

切换知识库用环境变量：

```bash
# 换到别的库
AGENT_KNOWLEDGE_DIR="D:/我的知识" node start.mjs

# 换回仓库内的样例库
AGENT_KNOWLEDGE_DIR=none node start.mjs
```

验证是实验 12：`node 12-real-vault.mjs`，同时查「能不能读到子目录」
和「写入会不会污染真库」两件事。

## 它怎么被接进去

`app/server.mjs` 启动 codex 时用 `-c` 参数注入
（把 mcp_servers.my_knowledge.command 指到 node，args 指到 server.mjs）。

**关键点：`-c` 覆盖只对本次启动生效，不会污染全局 `config.toml`。**
这就是「给自己的 App 单独配工具」的正确姿势。

## 怎么验证它真的通了

1. 协议层：直接喂 JSON-RPC 给 `server.mjs`，看它回不回 `tools/list`
2. 注册层：问 app-server `mcpServerStatus/list`，确认 `my_knowledge` 在里面
3. 行为层（`04-my-tool.mjs`）：问一个只有我的知识库才有答案的问题

三层都验过。行为层的实测输出：

```
=== agent 用到的工具 ===
- [我的 MCP] my_knowledge/knowledge_search ...

=== agent 最终回复 ===
结论：Agent Lab 里所有新建的实验脚本必须使用**两位数字前缀**，例如 `05-xxx.mjs`。

=== 结论 ===
[PASS] agent 调用了我自己写的 MCP 工具
[PASS] 答案来自我的知识库（含两位数字前缀规则）
```

## 一个真实的坑（值得记住）

第一次测试时 agent **没用我的工具**，而是跑去翻 Obsidian 记忆库和 MemoryLake。

原因：工具存在 != 模型会用。当环境里同时有好几个都能「查资料」的工具时，
模型会挑它更熟悉的那个。

解法：在 `knowledge.md` 里显式写了路由规则——

> 涉及「我的个人开发知识、规则、偏好、项目约定」的问题，必须优先调用 my_knowledge 服务。
> 不要去翻 Obsidian 记忆库、MemoryLake 或其它目录来找这类答案。

加了之后才稳定走我的工具。

**这是 agent 工程里非常重要的一课：工具的可发现性和优先级，和工具本身的功能一样重要。**

另外，即使加了规则，实测仍有抖动（同一条问题，一次走我的工具、一次手动执行脚本）。
真实系统的可靠性就是这样，别指望一次就稳。

## 后来又挖到两个真正的根因（这才是抖动的原因）

写规则只是让模型「愿意用」，但实测里还有两次失败，查下去发现是两个独立问题：

### 根因一：工具被「延迟暴露」了
MCP 工具默认不是直接摆在模型面前的，而是挂在“工具搜索”后面：
模型得先调一次 tool_search，才能看见 `knowledge_search`。
实测里模型没搜，于是自信地说「这个会话没给我这个工具」，然后放弃。

证据：`mcpServerStatus/list` 里明明有 2 个 `my_knowledge` 工具，
但模型的回合里看不到它，而去调了一堆 `list_mcp_resources`。

解法：在 `codex-home/config.toml` 里把这个服务从「延迟暴露」里拿出来，直接摆到台面上：

```toml
omit_tools_from = ["deferred"]
```

改完再跑 `04-my-tool.mjs`，模型第一件事就是直接调 `knowledge_search`。

### 根因二：工具没说自己是只读的

工具能看见了，但每次调用都卡在审批上：

```
参数={"query":"Agent Lab 项目 新建实验脚本 命名要求","limit":5}
返回: {"message":"user rejected MCP tool call"}
```

不是人拒绝了，是脚本没接审批请求，内核默认当拒绝。
而它会要审批，是因为我的工具**从来没说自己是不是只读的**——
内核看到没声明，就按「可能有破坏性」处理（看 `mcp_tool_call.rs` 的
`requires_mcp_tool_approval`：没声明 readOnlyHint 就按可能破坏处理）。

解法不是去放宽审批，而是让工具如实描述自己：

```js
// knowledge_search：只是读
annotations: { readOnlyHint: true, openWorldHint: false },

// knowledge_add：会写文件，所以刻意不声明，审批留着
```

**这一课比上方那个规则重要：工具声明得不准，安全闸门就会要么拦错、要么放错。**

两个根因都修完后，实测：

```
=== agent 用到的工具 ===
- [我的 MCP] my_knowledge/knowledge_search  参数={"query":"Agent Lab 新建实验脚本 命名要求","limit":5}
  返回: ...必须用两位数字前缀，例如 05-xxx.mjs...

=== 结论 ===
[PASS] agent 调用了我自己写的 MCP 工具
[PASS] 答案来自我的知识库（含两位数字前缀规则）
```

# 工具面污染：agent 每一轮到底背了多少工具

这是上面那个「工具会抖动」真正的环境级根因。

Agent Lab 最早是直接继承全局 `~/.codex/config.toml` 的，
而那份配置里挂着插件、远端应用、IDE 桥等一大堆服务。实测：

| | 全局配置 | 独立配置（`codex-home/`） |
|---|---|---|
| MCP 服务数 | 7 | 1 |
| 工具总数 | 32 | 2 |
| 「我的知识」占比 | 2/32 | 2/2 |
| 启动后 6 秒内后台报错 | 3 条（HTTP 502 重试） | 0 条 |

原因有两层：

1. **每一轮都要把全部工具的说明书塞进上下文**。工具越多，越贵，
  而且模型要在 32 个里挑一个，选错的概率天然更高。
2. **有一批工具是坏的**。全局配置里有的服务指向没在跑的端口，
   启动后在后台反复重试，刷出一串 `HTTP 502`。

解法：给这个 App 一份**独立配置目录**（`codex-home/`），只挂它真正需要的服务。
app/server.mjs 启动内核时把 `CODEX_HOME` 指过去；
想改回继承全局，把 `AGENT_CODEX_HOME=global` 传给它就行。

验证就是实验 11：`node 11-tool-surface.mjs`，同一套参数跑两次，只有配置目录不同。

顺手踩到一个坑，值得单独记：

> `-c mcp_servers.idea.enabled=false` 这种写法**关不掉服务，反而会把配置弄坏**。
> `-c` 覆盖是「换掉这个 key」而不是「合并」：一写就只剩 `enabled=false`，
> transport 字段没了 → `invalid transport` → app-server 直接起不来。
> 所以隔离要用独立 `CODEX_HOME`，别用一串 `-c`。

**这一课的结论：agent 的「能力」不是免费的。每多挂一个工具，都在扣上下文预算和决策准确率。**
能收窄工具面的地方，就收窄。

# 每一圈的成本：把「花了多少」拆成「哪一圈花的」

前面知道了一共花了多少 token。但那是个总数，不足以做决策：
你到底该改哪里有？是话太多，还是工具吐回来的东西太多？

答案是：**贵在工具的返回上，不在你打的字上。**

## 怎么把它拆出来

两份信息本来就都在，只是躺在不同的管道里：

- **内核探针**（走 stderr）：这是第几圈、刚结束时上下文多大
- **工具事件**（走 stdout）：调了哪个工具、参数是什么、返回是什么

`app/server.mjs` 把两边按圈对上：探针说「第 N 圈结束」就把这一圈的账封存，
把期间收到的工具条目（参数 + 返回的字节数）一起上报给界面。
**没改内核，没重编译。**

## 踩到的坑：顺序不保证

第一版里，探针一到「结束」当场就播报账单，结果账单上的工具体积经常是 0——
因为工具结果走的是另一条管道，有时比那行探针晚一点点才到。

我以为的修法是「等 150ms 再结账」。那是错的：下一圈的「开始」探针紧跟着就来，
会把账本清零，等一拍只能读到 0。实测就是这样打的：

```
=== 桥收件的真实先后顺序 ===
  探针  第 1 圈开始
  工具  mcpToolCall
  账单  第 1 圈（1 次工具）
  探针  第 1 圈结束
  探针  第 2 圈开始
```

正确的做法不是睡一觉，而是**换个结账时机**：
探针说「第 N 圈结束」只把账封存（pending），等下一次「开始」或整轮结束再结账。
这样晚到的工具结果会被补进已经封存的那份账里，最后一圈也不会漏。
顺手加了一条：新的一轮从零起算，否则这轮的「第 1 圈」会去跟上一轮比，凭空冒出一个负数。

**这一课的结论：跨进程拼数据时，别用 sleep 赌顺序，用状态机把时序问题变成确定性问题。**

## 实测证据（实验 13）

`node 13-loop-cost.mjs` 问一个必须查知识库的问题，界面上就长出这样的卡片：

```
第 1 圈结束 · 上下文 12,199 token
  · 工具 my_knowledge/knowledge_search  5.5 KB
     {"query":"苍穹开发 select 漏字段 报错","limit":5}
第 2 圈结束 · 上下文 12,467 token（比上一圈 +276）
  · 这一圈没调工具
```

一句话答案要背 5.5 KB 的资料回来——**你打的那句话只占几十字节。**

## 实测的意外收获：模型搜不到答案时会反复搜

写这一节时顺手在界面里试了一个「库里本来就没存」的问题，看账单长成这样：

```
第 1 圈 上下文 15,410 token · 工具返回 18.4 KB
第 2 圈 上下文 26,582 token（+11,172）· 工具返回 2 次 / 40.7 KB
第 3 圈 上下文 53,157 token（+26,575）· 工具返回 4 次 / 107 KB
第 4 圈 上下文 71,358 token（+18,201）· 工具返回 4 次 / 59.7 KB
第 5 圈 上下文 75,629 token（+4,271）· 这一圈没调工具
```

模型换了 9 个关键词搜同一件事，上下文从 15K 涨到 75K —— **翻了 5 倍，就为了确认「库里没有」。**
这不是模型笨，是没有技能时的自然行为：搜不到就换个说法再搜。
但它同时暴露了两件事：

1. **搜索工具自己吞掉了这个错误**：搜不到时它应该直接说「没有匹配」并停下，
   而不是把整个知识库片段大把大把吐回去让模型自己找。
2. **没有「搜过就算了」的记忆**：模型不知道刚刚已经搜过，于是重复劳动。

两个都是工具设计问题，不是模型问题。这就是为什么成本可视化值得先做：
**只有先看见钱去哪了，才知道下一步该优化哪里。**

跑法：先 `node start.mjs`，再 `node 13-loop-cost.mjs`。

# 修工具：为什么搜不到时要直接说「没有」

上面那 5 倍浪费，修起来其实是**改工具，不是改提示词**。

## 三个真问题（都在搜索工具自己身上）

### 一、整段 Markdown 原样回传

旧版按空行切段，段落里**只要有一个词命中就返回整段**。
长笔记一段上千字，一次查 10 条就是 40 KB——全部进下一圈上下文，还要跟着转好几圈。

修：单条结果截到 600 字。实测单次查询最大返回从 40 KB 降到 11 KB，常见问答在 2 KB 左右。

### 二、中文没有空格，整串词永远匹配不上

这是个不显眼但对中文库是致命的坑。旧版按空格切词，
所以「新建实验脚本 命名要求」里的「命名要求」被当成**一个词**。

而「命名要求」这四个字在库里从来没连写过（更常见的是「命名」和「要求」分开出现），
所以这个词永远匹配不上。等于中文查询里有一半的词是废的。

修：加了个零依赖的分词——中文按**二字滑窗**切（「命名要求」切成「命名」「名要」「要求」），
英文数字按整词切。不需要装分词库，中文召回率就够了。

### 三、Agent / Lab 这种词把无关段落全捞上来

旧版把每个词都算 1 分。但 Agent、Lab 这类词在整个库里到处都是，毫无区分度；
而 longnumber 这种词一出现就基本锁定了答案。旧版对两者一视同仁。

更糟的是「碰到任意一个词就算命中」：问「Agent Lab 的命名要求」时，
所有提到过 Agent 的段落都会被捞回来，真正的答案反而被 limit 切掉了。

修：换成**词频稀有度加权 + 覆盖率门槛**：

- 越稀有的词权重越高（粗糙的 IDF，几行代码）
- 判断标准是「覆盖了查询里多少分量」，不是「碰到任意一个词」
- 覆盖率低于 35% 就直说没有

## 效果（同一个问题，改前 vs 改后）

问题是「Agent Lab 新建实验脚本有什么命名要求」——**库里本来就没记**。

| | 改之前 | 改之后 |
|---|---|---|
| 转了圈数 | 5 圈 | 2 圈 |
| 最终上下文 | 75,629 token | 10,883 token |
| 工具返回 | 9 次 / 8.9 KB | 1 次 / 304 B |
| 模型最后说 | 反复换词搜了 9 遍 | 直接答「库里没有」 |

**下降 85%，而且答案更诚实了。**

## 这一课最值钱的地方

那 5 倍的浪费，从头到尾**不是模型的毛病**。
模型的每一个动作在它拿到的信息下都合理：搜索结果看着像答案但又不是，那就换个词再试试。

问题出在工具**没有把话说清楚**：搜不到就返回一堆沾边的，
等于告诉模型「这里有东西，但你没搜对」。

> **工具的返回值是给模型看的提示，不是给人看的搜索结果。**
> 返回一堆「可能相关」，模型就会反复试探；明确返回「没有」，它就停了。

顺带一条：返回里那句「换关键词也没用，不要反复搜索」，作用比前面所有代码改动加起来都大。
这是工具的**说话方式**在纠正模型的行为，比在外面加循环上限便宜得多。

跑法：`node 14-search-cost.mjs`（不需要起 App，直接量工具返回体积）。

# AI Agent 工作原理

## 一句话

**Agent = 大模型 + 工具 + 循环 + 上下文。**

普通聊天机器人是一问一答。Agent 的区别是模型能**动手**（执行命令、改文件、调接口），
并根据动手的结果**继续决定下一步**，直到任务结束。

## 我在真实运行中抓到的证据

实验 `02-turn-trace.mjs` 让 agent「建一个 hello.txt，然后确认它存在」，
下面是从真实事件流里摘出的关键帧（`trace.log`）：

```
 1510ms  turn/started              ← 一轮开始
 5707ms  item/started   [reasoning]        ┐ 模型第 1 次思考
 6257ms  item/completed [reasoning]        ┘
 7303ms  item/started   [fileChange]       ┐ 动手：写文件
12514ms  item/completed [fileChange]        │ 改的是 hello.txt
12515ms  turn/tokenUsage/updated            ┘ 累计 21852 tokens
14801ms  item/started   [reasoning]       ┐ 模型第 2 次思考（看到工具结果后）
15270ms  item/completed [reasoning]       ┘
15537ms  item/started   [mcpToolCall]     ┐ 动手：跑命令 ls -l hello.txt
20389ms  item/completed [mcpToolCall]       │ 工具返回了结果
20400ms  turn/tokenUsage/updated          ┘ 累计 43832 tokens
23057ms  item/started   [agentMessage]    ┐ 模型收尾，给出结论
23330ms  item/completed [agentMessage]     │
23335ms  turn/tokenUsage/updated          ┘ 累计 65841 tokens
23767ms  turn/completed                   ← 这一轮结束
```

注意这里面最关键的一点：

> **每一次「思考 -> 动手 -> 拿到结果 -> 再思考」之间，token 用量都在涨。**

21852 -> 43832 -> 65841。这不是浪费，这正是 agent 的工作方式：
**每一轮都要把「之前发生的全部事情」重新发给模型一次**，模型才能知道
「我刚才写了文件，现在要确认它」。

理解这一点，你就理解了 agent 工程里 80% 的成本与性能问题从哪来。

## 四个角色（对上代码）

| 角色 | 职责 | 在 Codex 源码里 |
|---|---|---|
| 模型 | 决定下一步做什么 | OpenAI Responses API |
| 工具 | 真正动手（读文件、跑命令、打补丁） | `codex-rs/core/src/tools/` |
| 循环 | 反复「问模型 -> 执行工具 -> 结果回灌」 | `codex-rs/core/src/session/turn.rs` 第 430 行的 `loop` |
| 上下文 | 决定模型每次能看到什么 | `codex-rs/core/src/context_manager/` |

`turn.rs` 第 149-161 行的注释就是这套循环的官方描述：

> 模型要么回一个函数调用，要么回一段文字。
> 如果是函数调用 -> 执行它，把输出送回模型，再问一次。
> 如果只有文字 -> 记进历史，这一轮结束。

## 三个层次的概念（容易混）

- **Turn（轮）**：一次「模型说话 + 执行它的工具调用」。可有多步。
- **Task（任务）**：一串 turn，到模型没有后续输出为止。
- **Thread / Session（会话）**：跨多次交互的持久历史，有 id，可恢复。

## 让 agent 靠谱的四个配角

光有循环会失控。生产级 agent 必须在旁边加上：

1. **上下文压缩** — 对话变长就摘要旧内容，否则会撑爆模型窗口
   （`compact.rs`，我在实验里真的看到了压缩相关的事件）
2. **沙箱与权限** — 危险命令要先审批，或限制在只读/工作区可写
   （`sandboxing/`、`exec_policy/`、`tools/approvals.rs`）
3. **工具规格化** — 每个工具都有参数 schema、校验、执行器、错误处理
   （`tools/handlers/`、`tools/runtime/`）
4. **知识注入** — 让模型知道「这个项目/这个人」的规矩
   （`AGENTS.md`、Skills、MCP，见下一节）

# 知识注入的三个层次

这是我这次真正实践过的部分：**不需要改内核，Codex 已经留好了口子。**

（现在在 App 左栏点「编辑我的知识」就能直接改，`knowledge.md` 存盘后开新会话生效。下面讲的是它背后的原理。）

| 层次 | 做法 | 适用 | 生效方式 |
|---|---|---|---|
| 文件约定 | 写 `AGENTS.md` | 项目规范、约定、禁忌 | 放进仓库，自动被读 |
| 会话注入 | 传 `developerInstructions` | 个人偏好、跨项目的规矩 | 每次开新会话时注入 |
| 能力扩展 | Skills / MCP Server | 可复用流程、接外部系统 | 按需加载 |

本项目用的是**第二层**：`app/server.mjs` 在调用 `thread/start` 时，
读取 `knowledge.md` 并作为 `developerInstructions` 传进去。

验证方式（`03-knowledge-check.mjs`）：在 `knowledge.md` 里要求模型
每次回复末尾带上 `[知识已生效]`，然后开一个新会话问它一句话：

```
=== 模型最终回复 ===
我是 Codex，一个在共享工作区中协助你读代码、改代码并验证结果的编程智能体。

[知识已生效]

=== 结论 ===
[PASS] 我自己的知识已成功生效
```

标记出现了，说明本地知识确实进了模型的上下文。

# 联网搜索：从「模型想上网」到「真的查到了」

这是从日志里挖出来的真实缺口，不是假设。某次会话里模型发起了这样的调用：

```json
{"type":"custom_tool_call","name":"web_search","input":"site:developers.openai.com Codex AI coding agent"}
```

内核回的是：

```
unsupported custom tool call: web_search
```

也就是说：**模型想联网，但我们一个字都给不出来。**

## 根因有两层

1. Codex 内核自带一个叫 `web_search` 的「托管搜索」工具。「托管」的意思是搜索结果由模型服务方提供——而 Agent Lab 走的是本地中转，没有那个端点（实测 `/v1/alpha/search` 返回 404）。工具却照样告诉了模型。**对模型许诺一个兑现不了的工具，比根本没有这个工具更糟。**
2. 我们自己也没有联网工具。

## 修法（两步，都不是改提示词）

1. 配置里 `web_search = "disabled"`，把那个空头工具摘掉；
2. 自己实现一个真能用的搜索服务（`mcp-web-search/`），按 MCP 插座接进去。

## 选搜索后端踩的两个坑

这部分比代码本身值钱，因为它演示了「工具返回错东西比报错更危险」。

- 先用 Bing 的 RSS 输出（`format=rss`）：搜「openai codex github」，返回的是**波兰门户网站 wp.pl 的首页**（多次复现）。
- 改用 Bing 的 HTML：不带会话请求时它会返回一批**填充内容**——搜的是 codex，回来的是「美国独立日」「iPhone 18 Pro」。
- 最后选 Brave 的 HTML（第一条就是 `github.com/openai/codex`，准），但它**会限流**，连续几次就给 429。

于是最终形态是三层：**Brave 优先 → 撞上 429 就冷却 30 秒并退到 Bing → 两个后端的解析结果都要过一道「相关性闸门」**。

每一层都是被实测逼出来的：

- **Brave 要排队限速**：同一时刻只允许一个请求在飞，两次之间至少隔 8 秒。之前不排队，连着问几句就 429。
- **冷却时长是量出来的**：先写 60 秒，嫌太久；实测约 30 秒就恢复，改成 30 秒。
- **闸门拦的是最危险的那种失败**：返回 200、看着像结果、内容全无关。判据是「查询里的词出现在标题/网址/摘要里」，并且至少要**两条承重**（结果少于 4 条时降到 1 条）。
- 这条门槛改过两版，都是被真实数据打出来的：第一版「有一条对上就放行」，8 条里混进 1 条沾边的，另外 7 条垃圾一起送出去；第二版加了比例门槛，又太严、正常搜索也被误杀。最后回到绝对条数——因为「填充内容」和「正常结果」的差别**不在于比例，而在于能不能对上**（实测填充内容是一整批地不相关：10 条里 0 条带查询词）。

### 闸门太松会变成「假相关」，比没结果还坏（2026-09-23）

这是后来挖出来的，也是本文里最值钱的一条排查。

现象：问「查 `openai/codex` 仓库最近更新」，模型一连搜了 **19 次**，一直换关键词，
最后既没收尾也没给出来源。第一眼很像模型不会用搜索。

实际是闸门太松。查询 `github.com/openai/codex latest releases` 切出来的词里
有 `com`（域名后缀），而 GitHub 的**首页**和**登录页**标题里都有 `github` + `com`，
于是各得 2 分，全部通过。「GitHub 教程」这类中文页也同样蒙混过关。
模型收到的是「看着相关、一点信息都没有」的结果——它只能换个词再搜。
**它不是在乱搜，是被假相关结果牵着走。**

修两处，都很小：

1. 停用词表：`com` / `www` / `http` / `latest` 这类几乎没有定位能力的词不参与计分。
   只滤纯基础设施词，不滤 `github`、`openai`、`codex` 这些真带信息的词。
2. 单条也要够格：原来只看「整批里至少两条能对上」，现在单条也有最低命中数
   （词多时要求 2 个，单词查询放宽到 1，否则正常查询会被一刀切死）。

效果：搜索次数从 **19 次降到 3 次**。真实指向仓库的结果仍然保留，
自检里两条新用例各盯一个方向——噪声被挡、真结果别误杀。

> 这一课和前面的「搜不到就直说没有」是同一条原则的两端：
> **工具的返回值是给模型看的提示。** 返回假相关，它就继续试探；
> 返回「没查到」，它才停。区别只在于闸门开得对不对。

### 又一层：同一个 URL，curl 能过、Node 被拒

修完闸门后仍然会失败，日志说 `brave: HTTP 429`。
本来打算当成外部限流、等一会儿就好——但先做了一件小事，结果推翻了假设：

```bash
curl -s -o /dev/null -w "%{http_code}\n" "https://search.brave.com/search?q=test"
# -> 200
```

**同一时刻**用 Node 打同一地址：

```
node -e "fetch('https://search.brave.com/search?q=test').then(r=>console.log(r.status))"
# -> 429
```

试过换请求头来缩小差异：裸请求、只带 UA、只带 Accept-Language、完整的一套 Chrome 安全头（`sec-ch-ua`、`Sec-Fetch-*`）——**全都是 429**。
所以差别不在请求头，在两个客户端的底层连接被对方按指纹区分了。
这不是「偶尔限流」，是稳定复现的客户端差异。

修法很小：**fetch 被挡时，用系统自带的 curl 重试同一个后端。**
两个系统都有 curl（Windows 10+ / macOS），所以不引入任何依赖；
只在失败时才起进程，正常路径不受影响。

效果是决定性的：端到端从「搜 19 次不收敛」变成「**搜 6 次、给出真实的 `0.155.1` / `0.157.0-alpha.8` 版本号和来源链接**」。

> 这里的教训不是「curl 比 fetch 好」，而是：**报错说「429」不等于原因就在外部。**
> 拿一个独立的工具打同一个地址，成本几秒钟，却能把「等它自己好」变成「本来就是我们的问题」。

顺带修了一个我自己新引入的误判：判定「是否被限流」时，我一开始扫的是整个事件流。
但事件流里既有模型发出的**参数**、也有工具返回的**结果**，
两者混在一起看，会把一次**成功**的搜索（真拿到了 Releases）判成「被限流」。
改成只读 `item.result.content` 的文本——那是工具真正返回给模型的东西。

顺带把两个「红灯指错地方」的问题也修了：
- 实验 17 原先超时就抛异常崩溃，连结论都不打印；现在超时只是一个观察结果，会分开报，
  并且把「搜索后端被限流（429）」归为外部状态（BLOCKED），不再一律报成「联网坏了」；
- 同一条脚本的 SSE 事件流被底层空闲超时掐断时也曾直接崩掉，现在会安静收尾，
  已经收到的事件仍用于出结论。

拦下之后不静默给空结果，而是明确回一句「两个后端都没成，原因分别是 X 和 Y，不要再换关键词」——因为含糊的失败会让模型换关键词反复重试，那是最贵的路径。

## 常驻进程才看得到的东西

一个容易踩的验证陷阱：限速状态活在进程里（上次请求什么时候发的、现在是否在冷却）。**每查一次就新起一个进程，这些状态全丢了，测出来的不是真实情况。**

所以实验 19 用一条长连接连着问 4 个问题，这才是 App 里的真实形态。实测结果：Brave 被限流那两次，它老老实实报「没连上」；没被限流的两次（`codex cli npm install`、`rust programming language`）都给出了相关且带链接的真实结果。**宁可不给，也不给垃圾**——这条守住了。

## 实测

- 实验 16：工具面里 `my_web_search.web_search` 可见，空头的托管工具已摘掉。
- 实验 17：真实问一句「Codex 仓库最近有什么更新」，模型连着调了 5 次搜索，最终给出带来源链接的中文答复，全程没有再出现 `unsupported custom tool call`。

# 苍穹开发专家：让这个 agent 真的懂苍穹

前面给 Agent Lab 接了自己的知识（`knowledge.md` + Obsidian 知识库）。那适合几十行的偏好和约定，但苍穹开发的知识不是这个量级——它是一整套 15 MB 的专家包：几百份 reference、可以直接抄的 Java 模板、API 知识库、写完用来查错的 lint 脚本。

## 不复制，而是链接过去

那套东西已经在 `~/.codex/skills/` 里了（平时用 Codex 写苍穹时用的就是它）。最省事也最不容易出错的做法，不是拷贝一份到这个 App 里——两个副本迟早各自变旧——而是让 App 的配置目录里有一条通向它的链接。

**要接两个技能，不是只接 `ok-cosmic`。** 工程自己的 `AGENTS.md` 写着「任何苍穹相关编码任务开始前，必须依次加载 `load-memory`、`ok-cosmic`」。分工是：

- `ok-cosmic` 管**「苍穹怎么写」**：插件时机与载体、API 快查表、可抄的 Java 模板、lint 脚本；
- `load-memory` 管**「这个项目怎么写」**：它去读工程里的 `.opencode/cosmic-sdk-reference.md`（字段查询规则、命名约定、基础资料取值方式）。

只接前者会出问题：代码能编译，但不符合项目规矩。接手这段时我一开始就只接了一个，是翻工程 `AGENTS.md` 才发现的。

```
agent-lab/codex-home/skills/ok-cosmic     ->  ~/.codex/skills/ok-cosmic
agent-lab/codex-home/skills/load-memory   ->  ~/.codex/skills/load-memory
```

这两条链接由 `app/server.mjs` 在启动时自动建立（Windows 用 junction，macOS 用普通目录软链），两边任何一边更新，另一边立刻就是新的。找不到某个技能时只提示一句，不会阻断 App 启动。

为什么这样就能生效：Codex 内核启动时会扫 `<CODEX_HOME>/skills/<名字>/SKILL.md`，把它们编成一份「可用技能清单」注入给模型。所以接上去之后，模型在一开始就看得见 `ok-cosmic`。

## 光接上不够，得让它真的去用
## 会话开在哪个项目，是个真选项

这一条是实际用起来才暴露的，但它比看上去重要。

`ok-cosmic` 的 Step 0 预检是从**会话的工作目录**逐级往上找 `ok-cosmic.json`。
一开始界面上没有项目切换，所有会话都开在 `C:\新建文件夹`（App 自己的上级目录）。
后果很具体：技能装得好好的、模型也真去读了，但预检永远报
「找不到配置文件」，于是它**拒绝写代码、只给概念**。
表面看像模型不给力，实际是会话根本没进那个项目。

修法很小：界面上加一个项目选择器，新会话把选中的路径当 `cwd` 传给
`thread/start`。清单写在仓库根的 `projects.json`：

```json
{
  "projects": [
    { "name": "Agent Lab（学习/试验）", "path": "C:/新建文件夹" },
    { "name": "sherp（苍穹工程）",   "path": "C:/hnsh/sherp" }
  ]
}
```

切换项目后要开**新会话**：已开始会话的工作目录是定住的（内核不让你中途改变
一个正在跑的项目根），界面会提醒一句。

意外的好处：指定 `cwd` 之后，内核会自己去找那个目录的 `AGENTS.md`。
实测返回里直接带着 `["C:\\hnsh\\sherp\\AGENTS.md"]`——
项目规则跟着会话走，不需要我们在 App 里再抄一遍。

验证在实验 26，两层证据：内核侧确认会话路径和自动加载的项目规则；
技能侧在那个目录下真跑预检，`errors=0 warnings=0`。

## 光接上不够，得让它真的去用

光把技能挂上，模型可能还是凭印象回答。所以 `knowledge.md` 里加了一条硬规则：涉及苍穹开发必须先加载 `ok-cosmic`，以它为准，不要凭记忆写。

实测（实验 18）问了一个典型问题——「单据插件和操作插件分别该在什么时机写业务逻辑，常用事件名是什么，优先用 kd-cd-cosmic-commons 的封装」——模型的表现是：

1. 真去读了 `ok-cosmic/SKILL.md`，不是假装读过；
2. **自动跑了技能里规定的 Step 0 配置预检**；
3. 预检发现这个工作区不是苍穹工程（没有 `ok-cosmic.json`），于是明确拒绝生成代码，只给概念说明；
4. 给出的类名和事件名（`kd.cd.common.plugin.AbstractBillPlugInExt`、`afterCreateNewData`、`propertyChanged`、`beforeDoOperation` 等）全部对得上技能包里的原文。

第 3 条尤其值钱：一个只说「好的我帮你写」的 agent 是危险的；知道「前置条件不满足就停下来问」的才是能用的。这个行为来自技能包里写好的约束，不是我们另写代码教会它的——这就是给 agent 写知识、而不是写提示词的价值。

## 项目规则是自动生效的，不用手工复制

这一点值得单独说，因为它改变了「该往哪放知识」的判断。

Agent Lab 自己有一份 `knowledge.md`，每次新会话注入。但那不是项目规则的唯一来源——**Codex 内核本身会去找工程根目录的 `AGENTS.md`**，找到就用。实测拿 `C:\hnsh\sherp` 起一个会话，内核回给你的 `instructionSources` 里就明明白白列着：

```
["C:\\hnsh\\sherp\\AGENTS.md"]
```

而且注入给模型的原文是这样的（截取）：

```
# AGENTS.md instructions for C:\hnsh\sherp
<INSTRUCTIONS>
# 项目规则
任何苍穹相关编码任务开始前，必须依次用 skill 工具加载：
1. `load-memory` — 加载项目记忆文件并遵守其全部约束
2. `ok-cosmic` — 苍穹开发主 Skill，按其规则执行
...
不再执行 Gradle 编译 ... 只需通过 IDEA MCP 静态检查以及 cosmic-post-lint.py
```

**这件事的意义**：项目的规矩应该写在项目自己的 `AGENTS.md` 里，跟着代码走、谁 clone 谁就有；App 的 `knowledge.md` 只放「跨项目的个人偏好」（比如用中文、先给结论）。两边的职责不要混——这跟前面「技能只链接不复制」是同一个道理。

（顺带：因为项目 `AGENTS.md` 已经强制要求加载那两个技能，我原先在 `knowledge.md` 里又写一遍「必须先加载 ok-cosmic」其实是重复的。留着无害，但要清楚哪一条才是权威。）

## 专家链路实战，以及 lint 的真实边界（实验 21）

实验 20 还只是「问问题」。实验 21 再往实战推一步：直接跑 `ok-cosmic` 自带的脚本，对一份**真实插件文件**做检查。全程只读、不碰代码、不跑 Gradle（项目规矩明确禁止）。

跑出来的三件事：

- **Step 0 预检**：`errors=0 warnings=0`，真实工程上通过。
- **post-lint 有真结论**：拿工程里一份真实的 `FinalApBillCostDepartmentQFilterBillPlugin.java` 去查，报出 `[WARN] L46 [B/SCENE-011] 继承型插件 @Override 未调用 super...`。这不是静默通过——静态检查真的在看代码。
- **lint 能抓真问题**：故意把 `new QFilter("id", QCP.equals, 1L)` 写成字符串 `"="`，lint 报 `[ERROR] [A/STYLE-024] QFilter 第二个参数必须使用 QCP 枚举（编译通过但运行时崩溃）`，退出码 1。

### 但它不查「select 字段够不够」

这一条是自己纠出来的，过程比结论值钱。

我本来想验证「漏 select 会不会被抓到」——项目记忆里写着「所有后续要用的字段必须在 select 里」，这条历史上栽过好几次。第一版样本我顺手把 `QFilter` 写成了字符串形式，lint 报的是 **QCP 那条**。而我的断言只要求「输出里出现 `select`/`字段` 字样」，于是**碰巧命中「字段」两个字就判了 PASS**。那是个假阳性，什么都没证明。

把干扰项全部排除（QFilter 改成合规的 QCP、`super` 也补上），只留「漏 select」这一个问题，lint 报的是：

```
[PASS] 检查通过！共扫描 1 个文件，未发现问题。
```

**结论**：lint 的 `STYLE-025` 只查「有没有指定 select 字段」（比如是否整实体全量加载），**不判断 select 的字段够不够**。而项目里最常见的那类事故（漏字段 → 运行时报「不存在名为 X 的属性」），恰恰属于后者。

所以：**lint 是网，不是全部防线。** 漏字段这类要么靠模型自己核对，要么靠运行时报错兜底。这一轮我把「抓不到」也写成了实验里的明确期望，免得以后有人误以为它管。

（这跟前面那两个坑是同一类问题：**断言写松了，绿灯就变成装饰**。测试通过不代表测到了想测的事。）

## 让它真的写代码，才发现 lint 漏了最核心的那条约定（实验 28）

前面所有实验验的都是「会不会用技能」和「看懂别人的代码」。
但「苍穹开发专家」真正的承诺是**它写出来的代码能过项目的规范**——这一条一直没验过。
实验 28 补上了：在真工程里让它按规则生成一个表单插件，再用项目自己的检查去判。

### 题目本身错了两次，都是模型提出来的

**第一次**我随手编了三个 `shfz_` 前缀的字段。模型拒绝生成，理由写得很清楚：
目标单据不明确，按项目规则不猜字段归属。**拒绝得对，是题目不对。**
改用在线元数据确认过的真单据（销售出库单 `im_saloutbill`，字段 `qty`/`price`/`amount` 均在 `billentry`）。

**第二次**它跑了 20 圈还没写到文件。查内核日志才发现不是它偷懒——
是我给它装的循环刹车在 20 圈处把它掐断了：

```
[AGENT-LAB] !!! 达到循环上限 20 圈，强制停止这一轮 !!!
```

真实编码任务的步数就是多：加载技能 → 读项目规范 → Step 0 预检 → 查在线元数据 →
核对 API 签名 → 读项目里同类实现 → 写文件 → 跑检查。20 圈不够用。
放宽到 60 圈后，它完整地写完了。

> 这是「保险值也是常量」的又一次验证：刹车默认值适合问答，不适合真实编码。
> 而且它报错的方式很坑——不是「撞上限了」，而是「文件没生成」，看起来像模型没干活。

### 拿到代码后，发现一个真问题
代码写出来了，lint 也给了 `[PASS]`。但有两条只有人（或更严的检查）才会看的对不上：

**模型在叙述里说**它「继承仓库优先封装的 `AbstractFormPluginExt`」；
**实际生成的代码继承的是** `kd.bos.form.plugin.AbstractFormPlugin`，也就是原生基类。
**说的和写的不是一回事，而 lint 判了通过。**

先把事实钉住（两边都查过）：

- 技能确实要求用封装类：`assets/FormPluginTemplate.java` 就是 `extends AbstractFormPluginExt`，
  `decision-matrix` 的表单插件行也把入口类指向它；
- 这个类真实存在：工程自带的 `kd-cd-cosmic-commons.jar` 里有
  `kd/cd/common/plugin/AbstractFormPluginExt.class`。

那为什么 lint 没拦？去看检查器就明白了——`lint/base.py` 里：

```python
UI_PLUGIN_MARKERS = [
    r"extends\s+AbstractFormPluginExt\b",
    r"extends\s+AbstractBillPlugInExt\b",
    ...
    r"extends\s+AbstractFormPlugin\b",      # ← 原生基类和封装类并列在同一个清单里
    r"extends\s+AbstractBillPlugIn\b",
]
```

这个清单只用来判断「这是不是一个 UI 插件」，**不区分该用哪一个**。
实测两次对比（隔离样本，各一个文件）：

```
extends AbstractFormPlugin      -> [PASS] 检查通过！共扫描 1 个文件，未发现问题。
extends AbstractFormPluginExt   -> [PASS] 检查通过！共扫描 1 个文件，未发现问题。
```

**结论：团队最核心的那条约定——「封装优先、原生兜底」——lint 根本不查。**

这比实验 21 那个「不查 select 够不够」更值得记：那一条是能力边界，这一条是**核心约定没被工具覆盖**，
而模型的自述又恰好会让人以为它做到了。三层叠起来（模型说得好 + lint PASS + 我们没细看），
得到的就是一个假绿灯。

所以实验 28 的判据分两层：lint 过了只算一层，**封装类、中文注释、@author/@since、分录 key、字段名、事件时机这六条要自己核**。
（每条的依据都写在了脚本注释里，不是拍脑袋定的。）

### 把这两个教训写回去，它就做对了

上面两个问题（沙箱权限导致停手、叙述与实际代码不一致）都不是「模型不行」，
而是**我们没告诉它这两件事**。把两条写进 `knowledge.md` 后重跑：

- 预检遇到权限错时，它说「这不是配置缺失，按已验证规则先申请沙箱外重跑」——
  然后真的重跑、通过了；
- 生成的代码里写的是 `extends AbstractFormPluginExt`，**叙述和代码对上了**。

最终结果：文件生成、lint PASS、六条人工核对全 PASS。

> 这一课对「转型做 agent 工程师」很有代表性：
> 性能问题的根因常常不在模型权重上，而在**你给了它什么信息、以及你的工具会不会骗它**。
> 同样的模型、同样的任务，改一段注入知识就从「停手不干」变成「干完且合规」。

### 但提醒是概率的，工具才是稳定的

两次全绿之后，同一道题又出现了一次「叙述说 Ext、实际写原生」。
注入的知识还在（会话里确认过），但它就是没被遵守——**模型的遵守是概率性的**。

所以把这条规矩落到了工具层面：在 `ok-cosmic` 的 lint 里加了 `STYLE-028`。
基类清单本来就在 `lint/base.py`，但那个清单只用来判断「是不是 UI 插件」，
原生和封装混在一起。新规则单独比对一次：

```
extends AbstractFormPlugin      -> WARNING STYLE-028（提醒封装优先）
extends AbstractFormPluginExt   -> 不报（本来就是要求的样子）
```

定级成 WARNING 而不是 ERROR：这是团队约定（B 层偏好），不是编译性错误（A 层红线）。
同时写进了 `coding-preferences.md` 的速查表。

> 给 agent 兑底时的取舍：**注入知识改变的是概率，工具检查改变的是边界。**
> 两者都要：知识让它大概率一次写对，lint 保证漏网的会被看见。

重复跑的稳定性：同一道题再跑一轮，模型同样写出 `extends AbstractFormPluginExt`，
lint 与六条人工核对全部 PASS（文件由模型自己写入临时目录，验证后清理）。
中途有一次红灯「没找到生成的文件」，查会话日志确认是外层 900 秒超时先杀掉了脚本、
turn 未完成所致，不是功能问题——所以这个实验运行时给足了 15 分钟。

# 走进内核：自己编译 + 埋探针

前面所有实验都是黑盒：只能看到 app-server 吐出来的事件。
要真正搞懂 agent，得进去看那个 `loop`。办法是**把 Codex 的源码自己编译一遍**，
在循环里插几行打印，然后让 App 用这个自己编的内核跑。

编译过程见 `BUILD-RUST.md`（这台机器没有 Visual Studio，走的是 Rust + mingw 的 GNU 路线）。
探针插在 `codex-rs/core/src/session/turn.rs`，就三处：循环前计数、每圈开头、每圈结尾
（结尾打印 `needs_follow_up` 和当前上下文 token）。

App 这边不用改内核代码：`app/server.mjs` 用 `CODEX_BIN` 环境变量选内核，
把内核对 stderr 的打印转发成 `lab/innerLoop` 事件，前端渲染成「内核探针」卡片。

## 实测证据（自编译内核，2026-09-22）

任务：「建一个 probe.txt 写入 probe-ok，然后用 cat 确认，做完就停」。
只读沙箱，所以写文件时弹了审批卡片，点「允许一次」放行。界面上的探针卡片依次是：

```
循环第 1 圈开始
循环第 1 圈结束：模型想继续? true；当前上下文 token = 22128
循环第 2 圈开始
循环第 2 圈结束：模型想继续? true；当前上下文 token = 22073
循环第 3 圈开始
  工具 · fastctx/run  { command: "cat probe.txt" }
循环第 3 圈结束：模型想继续? true；当前上下文 token = 22319
循环第 4 圈开始
  模型给出最终答复
循环第 4 圈结束：模型想继续? false；当前上下文 token = 22260
```

这一屏就是 agent 的完整心跳，一眼能读出三件事：

1. **一次任务 = 转了好几圈**，不是一个请求。这里转了 4 圈才收工。
2. **每圈结束都要问一句「模型还想继续吗」**。前三圈都是 `true`（它还要动手或确认），
   第 4 圈变成 `false`，循环才退出。这就是 `needs_follow_up` 这个开关在干活。
3. **停不停不是谁规定的步数，是模型自己决定的**。所以工程上的第一道保险就是给它加个上限。

注意 token 不是一路涨：22128 -> 22073 -> 22319 -> 22260。
这个数不是「这次请求发了多少」，而是「上一轮模型报的 token 数 + 这之后新加进去的东西估算值」
（`context_manager/history.rs` 的 `get_total_token_usage`）。写完文件那一圈，历史被重建，
数字就可能回落。所以别把它当成单调递增的计数器看，它是「当前上下文大概多满」。

**这也是 agent 工程里最核心的成本模型**：每一圈都要把整个上下文重新发一遍给模型，
所以省 token 的正确方向不是「少说话」，而是「别让没用的东西留在上下文里」。

跑法：`CODEX_BIN="C:/dev/codex/codex-rs/target/x86_64-pc-windows-gnu/debug/codex.exe" node start.mjs`。

# 改内核：给循环装一个刹车

看懂循环之后，第一件该做的事不是加功能，是**加限制**。

因为循环停不停是模型决定的，模型就可能停不下来：一直重试、一直找错方向、一直循环调用工具。
生产级 agent 必须有硬上限，这是第一条保险。

## 改在哪

`codex-rs/core/src/session/turn.rs` 的 `loop` 最顶上，加一个圈数检查。

关键不是「加个 if」，而是**加在哪一行**：

```rust
let agent_lab_max_iterations: u32 = std::env::var("AGENT_LAB_MAX_ITERATIONS")
    .ok().and_then(|v| v.parse().ok()).unwrap_or(20);

loop {
    agent_lab_iteration += 1;
    // 刹车放在循环体最顶上
    if agent_lab_iteration > agent_lab_max_iterations {
        eprintln!("[AGENT-LAB] !!! 达到循环上限 {} 圈，强制停止这一轮 !!!", agent_lab_max_iterations);
        sess.send_event(&turn_context, EventMsg::Warning(WarningEvent {
            message: format!("达到循环上限 {} 圈，已强制停止这一轮（Agent Lab 保险）。", agent_lab_max_iterations),
        })).await;
        break;
    }
    ...
```

我在第一次写的时候差点把它放在 `if !needs_follow_up { ... break }` 那个分支旁边。
那样是错的。因为循环里还有**别的 `continue`** 会跳回顶部绕开它：

- `run_auto_compact` 之后（上下文压缩完继续干活）
- stop hook 要求继续（`should_block` 分支）
- guardian 预算耗尽后的重试
- 采样报 `ContextWindowExceeded` 时的补偿

放在最顶上，所有路径都绕不过去。这个判断花了我一分钟，但价值远超这一分钟——
**保险丝要装在总闸上，不是装在某一个插座上。**

## 为什么用环境变量，不改配置文件

`AGENT_LAB_MAX_ITERATIONS` 读环境变量、默认 20。这样不用重编译就能做实验，
也能在 App 启动时按需调（`app/server.mjs` 传 `process.env` 给内核，天然透传）。

## 实测证据（实验 07）

`node 07-loop-brake.mjs` 会把上限压到 **2 圈**，再给一个正常要转 4 圈的任务。
目的就是故意让它撞墙：

```
内核 | ===== 循环第 1 圈开始 =====
        [模型收尾] "I'll create brake.txt with the content you specified."
内核 | 循环第 1 圈结束：模型想继续? true；当前上下文 token = 21045

内核 | ===== 循环第 2 圈开始 =====
内核 | 循环第 2 圈结束：模型想继续? true；当前上下文 token = 21062

内核 | !!! 达到循环上限 2 圈，强制停止这一轮 !!!
   [警告] 达到循环上限 2 圈，已强制停止这一轮（Agent Lab 保险）。
   [turn 结束] status=completed

=== 结论 ===
[PASS] 刹车生效：模型还想继续，但被内核拦住了
```

第 2 圈结束时模型还想继续（`true`）。**换作没有刹车，这里就会一直转下去。**

## 第二课：让刹车会说话

第一版加完，我在界面里试了一遍，发现**内核已经报警了，但界面上什么都看不到**。

原因在 `app/public/app.js` 的 `onEvent`：它用一个 `switch (m)` 分发事件，
而那里没写 `warning` 分支，于是这条事件掉进 `default: break` —— 被默默丢掉。

**这不是内核的 bug，是前端的 bug**：内核喊了，界面没接住。
改法就是补一个分支：

```js
case "warning":
  // 内核主动报警（比如碰到循环上限）。不显式处理就会被 default 默默丢掉，
  // 用户只看到「跑完了」，不知道为什么停。
  addCard("error", "内核警告", p.message ?? "");
  break;
```

补完再触发一次，界面上就多了那张红边卡片：

```
内核探针  [AGENT-LAB] !!! 达到循环上限 2 圈，强制停止这一轮 !!!
内核警告  达到循环上限 2 圈，已强制停止这一轮（Agent Lab 保险）。
```

（截图见对话记录：改了文件 → 审批放行 → 探针第 1、2 圈 → 撞上限 → 红卡。）

**这是 agent 工程里另一个反复出现的教训**：任何一个「静默失败」的入口，
都会让上面所有层的努力白费。内核愿意报，桥愿意传，界面不接，用户就等于什么都没收到。

顺带也说明了「端到端验证」为什么不能省：实验 07 里这个警告**是能看到的**（脚本自己读 stderr），
如果只看那个就一定以为没问题。**只有真的走一遍界面，才暴露得出来。**

## 对照实验：上限不该在正常路径上生效

同一个任务、同一个内核，只把上限从 2 改成 10，结果就从「被砍」变成「自己收工」：

```
内核 | 循环第 1 圈结束：模型想继续? true；  token = 21105
内核 | 循环第 2 圈结束：模型想继续? true；  token = 21046
内核 | 循环第 3 圈结束：模型想继续? false； token = 21103
        [模型收尾] "已创建 brake.txt，内容为 braked；确认命令输出也是 braked。"
=== 结论 ===
[FAIL] 刹车没生效   ← 脚本在如实报告：这次它没撞到上限
```

这里 `[FAIL]` 不是故障，是脚本的判断条件写的是「有没有撞到上限」。
**上限是保险，不是流程**：它常在正常路径上生效，说明阈值设小了。

（`brake.txt` 两次实验都落了盘：一次是强制停止前已经写完，一次是正常收工。）

## 端到端再确认一次（实验 08）

实验 07 是绕过 App 直接跟内核说话的。真正的产品链路上还多一层：
界面 -> `app/server.mjs` 的 HTTP 桥 -> 内核。所以再跑一次 `node 08-app-e2e.mjs`，
它走 App 自己的接口发任务、从 SSE 里收探针：

```

新会话: 01a0c75f-ac6c-7b92-a586-7218aec83043
>> 发任务：用一句话说明你是谁，然后结束。
  内核探针 | ===== 循环第 1 圈开始：准备把上下文发给模型 =====
  内核探针 | 循环第 1 圈结束：模型想继续? false；当前上下文 token = 21917

这一圈 `needs_follow_up` 直接是 `false` —— 纯问答不需要动手，一圈就收工。
**「转几圈」不是固定的，是任务难度决定的**：要改文件、要验证的任务就得多转几圈。

（`ready=false` 是正常的：`/api/info` 是在 `initialize` 之前读的。）

### 再加一层：连沙箱一起验

上面那轮是只读的纯问答，压根没碰沙箱。再跑一轮 `workspace-write` + 真跑 shell 命令：

```

  探针| 循环第 1 圈结束：模型想继续? true；当前上下文 token = 21378

         已创建 e2e-sandbox.txt 并确认内容为 full-chain-ok。

文件确实落盘（`cat` 输出 `full-chain-ok`）。到这一步，四层全部打通并各自有证据：

```
界面  ->  app/server.mjs  ->  自编译内核  ->  Windows 沙箱
 ✓         ✓                    ✓              ✓
```

**这一轮最有价值的不是「又跑通一次」，而是推翻了上一轮的一个结论。**
之前我把「沙箱起不来」当成这台机器的环境限制，写在限制清单里准备以后再说。
实际查下去才发现：**不是沙箱坏，是我们没把它的两个 helper 编出来。**
（细节见下节。）

## 重编译踩到的坑

改完 Rust 第一次编译直接 **OOM 挂了**：

```
memory allocation of 2097152 bytes failed
```

不是代码错，是 cargo 默认按 CPU 核数（这台 16 核）并行跑一堆 rustc，
32 GB 内存被吃穿。**解法：`cargo build --bin codex -j 4`** 限制并行度。

第二次编译又失败，报的却是文件删不掉：

```
error: failed to remove file `...\debug\codex.exe`
Caused by: 拒绝访问。 (os error 5)
```

因为 App 还在跑，Windows 不允许覆盖正在执行的 exe。
**解法：先把 App 停掉，或者把旧的 `codex.exe` 改名（重命名是允许的，删除不行）。**

这两个坑跟 Rust 没关系，是「在 Windows 上热更新一个正在运行的程序」的通用问题。

## 意外收获：把 Windows 沙箱也修好了

前面几轮一直有个碍事的老毛病：agent 跑 shell 命令时沙箱起不来。
改成写文件（`apply_patch`）能过，一让它跑命令就报错，
所以之前得靠降级、走 MCP 的 bash 工具绕过去。

这次顺手查明白了原因。Codex 在 Windows 上的沙箱不是纯 Rust 实现的，
它要调两个**独立的小程序**：

| 程序 | 干什么 |
|---|---|
| `codex-windows-sandbox-setup.exe` | 创建沙箱专用账户、配防火墙规则（需要管理员权限，只跑一次） |
| `codex-command-runner.exe` | 在沙箱身份降下来的进程里真正执行命令 |

官方安装包会把这俩放在 `resources/` 里。**但我们 `cargo build --bin codex` 只编了主程序，
这两个 helper 根本没生成**，于是沙箱一启动就找不到人干活。

找 helper 的逻辑在这里（`windows-sandbox-rs/src/helper_materialization.rs`）：
先在 `codex.exe` 同目录找同名文件，再找同级 `resources/` 子目录。
所以只要把两个 helper 编出来、放在 `codex.exe` 旁边就行：

```bash
cargo build -p codex-windows-sandbox -j 4
```

产物会直接落在 `target/x86_64-pc-windows-gnu/debug/`，
也就是 `codex.exe` 所在的同一个目录，连拷贝都不用。

验证（跑命令成功、结果正确）：

```
$ codex exec --sandbox workspace-write --skip-git-repo-check \
    "run the shell command: echo sandbox-ok > shelltest.txt ; then cat shelltest.txt"

codex
Ran it. Output:
  sandbox-ok
Created `shelltest.txt` in `C:\Users\hero1157\AppData\Local\Temp\sbtest`.
```

文件确实落了盘（`cat shelltest.txt` 输出 `sandbox-ok`）。
**所以「沙箱坏了」这个结论是错的，真相是「没把沙箱组件编出来」。**

这也补上了 BUILD-RUST.md 里缺的一步：`cargo build --bin codex` 不够，
自编译内核想正常干活，得把 `codex-windows-sandbox` 这个包一起编。

## 上下文压缩：那个把 token 拉回来的东西

知识注入那一节提到过一次「上下文压缩」，但那时只是从代码里读到它存在。
实验 09 把它变成了看得见的一帧。

### 为什么要压

前面说过，每一圈都要把之前发生的全部事情重新发给模型一次。
那问题就来了：一直干下去，上下文总会填满模型窗口。填满之后要么报错，要么变慢变贵。

**压缩就是官方的解法：把旧历史交给模型摘要成一段短文字，把原始内容丢掉。**
它不是额外的一次请求，而是同一轮循环里的一个分支（`turn.rs` 的 `should_roll_over`），
但触发检查发生在**每一圈开始之前**：先看当前上下文超没超门槛，超了就先压缩，再发下一圈。
这一点很关键，也直接决定了实验 09 的门槛该怎么取。

### 怎么才能看到它

真实模型窗口是几十万 token，等它自然撞上要烧掉大量 token。
实验 09 直接把门槛压到 **9000**（当前会话基础上下文约 9200，第一圈结束就越线，第二圈开始前必触发）：

```bash
node 09-compact-watch.mjs
```

> **门槛是个跟着环境变的常量。** 工具面、模型、知识库都会影响基础上下文大小。
> 稳的取法是让它低于「第一圈结束时的上下文」，别贴着后面几圈去卡。
> 这个数已经改过两回：工具面收窄后 15000 -> 10000，换模型后又 10000 -> 9000。
> 下次红灯先怀疑常量过期，别先怀疑压缩坏了。

### 实测输出（2026-09-22）

```
循环第 1 圈结束：模型想继续? true；当前上下文 token = 9224
>>> [上下文压缩] 开始（第 1 次）
<<< [上下文压缩] 完成
[警告] Heads up: Long threads and multiple compactions can cause the model to be less accurate.
循环第 2 圈开始（用的是压缩后的上下文）
循环第 2 圈结束：当前上下文 token = 12206
>>> [上下文压缩] 开始（第 2 次）
...（继续）

=== 结论 ===
看到的压缩次数: 2
活跃上下文轨迹: 9224 -> 12206（每次越线都会被拉回）
累计用量轨迹: 9154 -> 13669 -> 24889 -> 29567 -> ...
[PASS] 压缩被触发：上下文涨到头时，内核做了摘要压缩
```

### 这一课真正的收获

两个数字看起来矛盾，其实一个是「当前多重」、一个是「累计花了多少」：

- **活跃上下文会被拉回可接受范围** — 压缩把旧历史摘要掉了，窗口没被撑爆
- **累计用量只涨不降** — 每一次 LLM 调用都是真金白银，压缩节省不下来

这就是 agent 成本的真相：**压缩解决的是「能不能继续跑」，不是「跑得便宜不便宜」。**
想让 agent 便宜，得从「少掉无用工具结果、少发几圈」上下手，而不是指望压缩。

另外注意模型自己会提醒：连续多次压缩会让它变糊涂。
所以生产系统里常见的做法是长任务开新会话、把关键结论写到文件里，而不是无限压迫同一个上下文。

## 成本可见：哪一条工具调用在烧钱

实验 09 看的是「一个会话要花多少」，但真正能优化的是**具体哪一条工具调用把上下文塞满了**。

这件事不需要改内核。工具调用的参数和返回本来就跟着事件到达前端，
只是之前只显示参数、没量返回。

界面现在多了两处：

1. **顶部一行读数**：`累计 xx token · 工具返回 N 次 / xx KB`
2. **每条工具卡片底部一行**：`进入上下文 ≈ xx KB`

实测一例（真在界面里跑的）：

```
累计 44,168 token · 工具返回 1 次 / 269 B

工具 · fastctx/run   { "command": "ls -1", ... }
进入上下文 ≈ 269 B
```

为什么要单看「返回」？因为参数是我们让它干的，而**返回内容是模型自己决定要拿的**。
一条 `ls` 才 269 B，但如果让它「把整个仓库读一遍」，返回就是几百 KB。
**这就是 agent 成本能被人为控制的地方：限制工具返回的体积，比省自己的提问有效得多。**

## 知识编辑：不离开 App 就能改

之前改 `knowledge.md` 要自己去找文件、手动编辑。
现在 App 左栏多了一个「编辑我的知识」按钮：弹出全文编辑器，保存写回 `knowledge.md`。

实测闭环（全在界面里完成）：

```
点「编辑我的知识」 → 写入一行「[界面测试] ...」 → 点保存
提示：已保存。开一个新会话生效。

新会话问：标着「界面测试」的那条原文是什么？
模型答：[界面测试] 这条是验证 App 内编辑知识的功能。
```
为什么必须开新会话：**知识是在 `thread/start` 那一刻注入的。**
已经开始的会话里，那份开发者指令已经进了上下文，改文件不会回溯修改它。

### 这条承诺，后来用实验 25 硬验了一遍

上面那轮是手工试的。这一轮把它变成一个有对照的自动检查——因为「新会话读到了」和「改文件对所有会话都生效」这两种情况，只看新会话是分不清的。

做法是插一条**能被客观检验**的临时规则，而不是靠模型自我描述：

```
在 knowledge.md 末尾临时加一条：
  你的每一条回复，第一行必须原样写出 ZK-7742-CHECK

会话 A（改动前就建好的）：没有口令   ✓ 符合预期
会话 B（改动后新建的）  ：ZK-7742-CHECK / 我是 Codex...   ✓ 承诺成立
回到会话 A 再问一次     ：仍然没有口令   ✓ 不被追溯改写
最后把 knowledge.md 还原，逐字节比对一致
```

三条加起来才说明白这条知识的真实语义：**它是会话创建时的快照，不是一个随时读的变量。**

用临时口令而不是「请复述标记」这类问法，是为了避免模型顺着你的话编——口令是这一轮现编的，旧知识里绝对没有，出现就只能是真读到了。这条做法比实验 03 那种「看有没有输出 `[知识已生效]`」更硬：那个标记本来就写在知识里，模型照抄也能过；口令换一次就知道是不是真读了。

**顺带一个观感**：这一轮是在真实界面上点着验的——点「编辑我的知识」、在框里补文字、点保存、看着提示变成「已保存」。整个过程比纯脚本直观得多，也正因为走了真实界面，才紧接着撞出上一节那个「过期审批卡片撒谎」的 bug。
这不是缺陷，是设计——上下文一旦发出就是不可变的，想让新知识生效就新开一轮。

## 会话历史回放：点一下能看到过去

左栏的会话列表之前只能切换，点进去还是空的。
现在点任意一个历史会话，App 会向内核要回这个会话的完整轮次（`thread/read` + `includeTurns`），
再把每一轮里的用户消息、模型回复、工具调用和它们的返回，按顺序重新画成卡片。

两个实现上的注意点：

1. 历史卡片不进 `itemNodes`。那张表是给「正在跑的会话」做增量更新用的，
   历史条目已经是终态，重新造一张卡就行，混进去反而会串。
2. 历史接口不带 token 数。所以另外存了一份会话用量缓存，回放时按会话 id 去取。
   取得到就显示真实数字，取不到就写「历史会话（token 用量未记录）」——不编造 0。

## 用量持久化：重启 App 也不丢

会话进行中，内核会推 `thread/tokenUsage/updated` 事件，但历史接口不回放这个数字。
桥接层顺手把每个会话的最后一个累计值记进内存，再落盘到 `.thread-usage.json`。

落盘不是每次事件都写：用量事件来得很密，先攒 1 秒再合并写一次，够用且省事。
启动时读回这张小表，所以关掉 App 再打开，老会话的用量还在：

```
发一轮任务 → .thread-usage.json 写入 {"01a0c782-...": 22146}
杀掉进程，重启 → 打开该会话 → 仍显示 22146
```

这里没有上数据库，一张 JSON 小表就够——这是本项目刻意的取舍，等会话数量真的撑不住再说。

## 中断：谁说了算

前面的循环刹车（实验 07）是**按圈数硬停**——上限是我们写死在代码里的，模型看不见、也无所谓，它只是被动地发现「前面没路了」。
中断按钮是另一回事：**人在跑的过程中随时喊停**。

这件事值得多看一眼，因为它回答了 agent 工程里最根本的一个问题：**谁在开车。**

看起来是模型在一圈一圈往下跑，其实每一圈的「要不要继续、能不能调这个工具、这次调用给多大权限」都是宿主程序决定的。
模型只负责提要求（“我要执行这条命令”），真正执行、真正说不的，都是内核这一侧。
中断就是这条主线最直接的体现：**你按下去，它就停。**

### 它是怎么做到的

内核里每一轮 turn 都带着一颗 `cancellation_token`（取消令牌）。
循环里几乎每一个可能卡住的 `await`——等模型回答、等工具跑完、等 MCP 返回——都挂在这颗令牌上（`or_cancel(&cancellation_token)`）。
所以中断不是「发个消息告诉模型别写了」，而是**从任务树上把这些 await 直接摘掉**。
命令已经开始跑也拦得住；更关键的是，**还没开始的后续步骤再也没机会开始**。

App 这边只做了三件小事，没有动内核：

1. `turn/start` 的返回值里直接带着 turn id，拿到就存好（不用等 `turn/started` 通知，否则刚点完发送就点停止会落空）
2. 发 `turn/interrupt`，参数是 `{ threadId, turnId }`——内核只认它认得的那一轮 id，报错了就拒
3. 内核把这一轮报成 `interrupted`，界面翻成「已停止」

### 实测输出（2026-09-22）

用实验 10 做的一个硬验证：给一个两步任务（先建 `A` 再建 `B`），**等第一步的工具真的跑完，再发中断**。
这样三个证据能同时对上，缺一个都说明不是真拦住：

```
   312ms [turn 开始] 01a0c78b-9c23-76f1-a30b-d067a25e12b4
       内核 | ===== 循环第 1 圈开始：准备把上下文发给模型 =====
  8336ms [工具完成 #1] mcpToolCall
  8336ms [发中断·首步之后] 已完成工具调用 1 次
  8384ms [中断回执] {}
  8384ms [turn 结束] status=interrupted

=== 结论 ===
turn 最终状态: interrupted
第一步产物: 已创建
第二步产物: 未创建
[PASS] 中断生效：第一步已落地，第二步被拦下，轮次标记为 interrupted
```

为什么这三个证据都要看：

- **第一步已落地** — 任务真的跑起来了，不是被提前掐掉
- **第二步未落地** — 循环是在中途断的，不是自己跑完了
- **状态是 interrupted** — 在内核眼里这是一次正经的终止，不是崩溃、超时或者报错

而且从点击到 turn 结束只隔了几十毫秒：模型还在生成、工具还没落地的时候，令牌一断，整棵任务树就散了。

### 两个容易搞混的点

**中断不等于撤销。** 已经写过的文件不会自己回去，已经发出去的请求也收不回答案。
它拦的是「后面还没发生的」，不是「已经发生的」。
这一点在真实系统里非常要命：一个 agent 跑了一半被你停掉，它留下的半成品状态是要人来收的。
所以很多系统会让 agent 把计划先写进文件，中断之后下一个 agent 才能接着做——这也解释了为什么「能停下来」和「能接着做」是两件事。

**停下来的会话没有坏。** 被中断那一轮记成 `interrupted`，接着发一条新消息，它会看得见之前发生了什么，正常继续。
这一点在实测里验过：中断后再问一句，模型照常回答。
循环可以断，会话不用重开——这是把「一轮」和「一段对话」分开设计的好处。

### 顺手抓到的一个界面 bug

这个功能做出来之后，一次截图暴露了问题：点了停止，对话区是**空的**——连刚发出去的那句话都不见了。
看着像「什么都没发生」，其实内核那边一切正常。

根因在前端：自己发出去的那句话，之前是**等内核回显**才画出来的。
网络一来一回的那段时间里，对话区什么都没有；手快在这段时间里点停止，回显就永远不会到了。
界面在撒谎，说「你什么都没发」。

修法是让界面别等：发出去的瞬间就先画一张自己的卡片，等内核回显到了再认领它（而不是再画一张）。
实测两种路径都对：

```
发完 120ms 就点停止 → 那句话说还在（1 张卡），状态「已停止」
正常跑完 → 用户卡片只有 1 张，没有重复
```

两个都验，是因为这修法的风险就在「重复」：画早了、回显又画一次，屏幕上就会出现两遍。
改「显示」的代码，验证必须同时盯住旧问题和新风险。

顺带把另一个同类隐患堵上：`新会话` 按钮和 `发送` 里的自动建会话可能同时发起，
两个请求都在飞的时候，后回来的那个会覆盖会话并清空对话区——刚发的话同样会没。
现在同一时刻只允许一次建会话，后来的等同一个结果。

## 侧边栏不跟着对话滚（布局锁定）

用一段时间就会发现：左侧会话列表一多，整个页面跟着对话一起上下滚，
想点历史会话得先把它「滚回来」。

根因是一个很典型的 grid 布局坑，三层叠在一起：

1. `body` 只有 `grid-template-columns`，**没有锁 `height`**——
   内容多高它就多高，整页滚动条出现在最外层；
2. 左右两栏作为 grid 子项，默认 `min-height: auto`——
   内容再长也不会被压缩，只会把父级继续撑高；
3. `.stream`/`.threads` 虽然写了 `overflow-y: auto`，但它们自身高度不受约束，
   「内部滚动」根本无从谈起——`scrollTop` 设上去也永远是 0。

修法三行，各锁一层：

```css
body { height: 100vh; overflow: hidden; }  /* 整页不许滚 */
.main, .rail { min-height: 0; }            /* 子项允许被压缩 */
/* .stream / .threads 的 overflow-y: auto 此时才真正生效 */
```

判断依据不是「看起来不滚了」，而是量出来的：body 的 `scrollHeight` 不再大于
`clientHeight`（整页无溢出），两个列表各自 `scrollHeight > clientHeight`
（内容超出时在自己内部滚）。这条验证写在了实验脚本里，改布局就能复跑。

# 一个只有点界面才会发现的 bug

这个 bug 是走真实界面撞到的——而在此之前，**我所有的测试都走 HTTP 桥或直连内核，全都测不到它**。

现象：点开左边的历史会话，历史正常显示；一发消息就弹这么一行：

```
发送失败 Error: {"code":-32600,"message":"thread not found: 01a0c8d9-..."}
```

原始 JSON 直接摔到用户脸上，看不出该做什么。

## 根因：两个很像的调用，职责完全不同

界面的 `openThread()` 只调了 `thread/read`——从磁盘读历史。它**漏了 `thread/resume`**。

```
thread/read    = 只读历史。会话在磁盘上，读完界面就有内容了。
thread/resume  = 把它变成「活会话」。只有活会话才能收新消息。
```

所以界面看起来一切正常，但内核的活会话表里根本没有这个 id；一发消息，内核如实回答「没这个会话」。

## 为什么它藏了这么久

因为 **App 不重启的话，之前的会话一直留在当前进程的活会话表里**。`thread/read` 之后直接发消息也能通。只有 App 重启过、会话已经不在活表里时，这个洞才露出来——而我之前那些自动化测试每次都新起进程、自己造会话，恰好绕开了这个场景。

修法是在 `openThread()` 里先 `thread/resume` 再 `thread/read`；顺手把原始 JSON 换成看得懂的中文提示（`humanError()`：认得出 `thread not found`、缺密钥、401 这几种，认不出就原样给 message，总比一串 JSON 强）。

验证分两步，都记在实验 23 里：

- **真实界面**：点开历史会话 → 发消息 → 模型正常回复（修复前这一步是 `thread not found`）；
- **自动检查**：起一个全新内核进程（模拟 App 重启过），先证明「只 read 就发消息」会被拒绝，再证明「resume 之后能通」。把这条契约固定住。

**这一课的教训是测试视角的**：走 API 的测试和走界面的测试，覆盖的是不同的路径。我前面那些实验把桥和内核测得很细，但整个「界面」这一层几乎没碰——所以一个一点就现的 bug 活到了现在。

## 顺着这条线，把审批按钮也验一遍（实验 24）

既然界面层没测过，那就补最有价值的那个：**审批按钮**。它是人唯一能拦住 agent 的地方，两个方向都必须有效果。

先在真实界面上手工点了一遍：

- 点「允许一次」→ 卡片变成「已回复：accept」、按钮变灰 → agent 继续跑完 → 文件真的落盘，内容是 `ui-approved`；
- 点「拒绝」→ 卡片变成「已回复：decline」→ 模型回的是「文件未创建：本次写入被拒绝。按你的决定停止，**没有改用其他方式绕过**」→ 文件确实不存在。

第二条尤其要紧：一个「拒绝之后偷偷换个命令写进去」的 agent，比没有审批更危险，因为它给了人虚假的安全感。

然后把这套固化成 `24-approval-ui.mjs`（走桥的 HTTP 接口驱动，和界面按钮打的是同一个 `/api/reply`）。

### 写这个脚本时踩的坑：我自己的测试制造了一个假红

拒绝那一段稳定地失败：文件被判为「被创建了」、模型回答里也没有承认被拒。但手工点、以及单独写的调试脚本，拒绝都是好的。

打开诊断输出，一眼看到问题：

```
[审批] item/fileChange/requestApproval -> accept  HTTP 200    ← 这一行不该有
[审批] item/fileChange/requestApproval -> decline HTTP 404
```

**`accept` 是上一段测试的残留连接回的。** 我收尾时只调了 `es.body.cancel()`，那个 SSE 读循环其实没停，还挂着「我决定 accept」这个回调。第二段的审批请求一来，**两条连接同时抢答**：残留的那条先说 accept 并且赢了；我真正的 decline 因为请求已被消费掉，只拿到 404。

说白了：**测试自己漏了连接，却伪装成「拒绝失效」。** 修法是用 `AbortController` 真正掐断（记得等一小会儿，让读循环里的 `AbortError` 被吃掉，否则它又会以未处理的 rejection 冒出来）。

**教训**：这类测试里，「回复被吞掉/被抢答」造成的假红，和真实的功能缺陷在表面上完全一样。诊断信息里带上 HTTP 状态码和「谁回复的」，是分辨它们最省事的办法——只看成败的话，我会一路往错误的方向查。

## 界面还会擒谎：过期的审批卡片

修完上面那条，界面还堆着一大批之前测试留下的审批卡片（页面一直开着，卡片就一直在；内核那边的请求早就没了）。顺手点了一个——它显示「已回复：accept」。

**但服务端根本没有这个请求。界面在撒谎。**

查下去是前端的问题：`reply()` 只 `fetch` 一下，**从不检查返回**。桥其实返回了 404 `{"error":"未知请求 id"}`，而界面照样把卡片标成「已回复」。

对审批这种安全闸门来说，这是最不能接受的一类错：**它告诉你「拦住了」，其实什么都没发生。** 人以为自己做了决定、agent 收到了，两边都是假的。

修法是检查 `res.ok`：失败时把卡片标红、写「回复失败：这个请求已经不在了」，并且不管成败都把按钮禁掉（失败也不能让人反复点）。

实验 24 里加了对应的检查：拿一个不存在的 id 去回复，桥必须明确报错而不是静默成功——静默成功的话，前端就无从判断，这类「撒谎」迟早复发。

**这两条连着看，是同一种病**：界面显示的成功，不等于事情真的成了。审核一个 agent 界面时，「它说成功了」和「它做成了」必须分开验证。

# 两个把「功能坏了」伪装起来的坑

这两个是同一类问题：**红灯是真的，但它指的方位是错的。** 值钱的地方不在修法（都是一行），在于怎么发现的。

## 一、`workspace-write` 会静默降级成只读

实验 07（循环刹车）和 10（中断）连着红了两次，报的都是「刹车没生效」「中断没生效」。第一反应是去查那两个功能——但探针显示**循环只转了第 1 圈就没了下文**，这不是刹车的表现，是这一轮压根没跑起来。

往下查，一共套了三层：

1. **第一层：实验读错了配置。** 这两个实验没设 `CODEX_HOME`，内核于是读了全局 `~/.codex/config.toml`，那份里的模型是 `mimo-v2.6-flash` —— 而本地中转上这个模型的上游是挂的，请求直接 503。表现是「第 1 圈开始」之后就没有下文，脚本却报「刹车没生效」。**修法：两个实验都显式指向 App 自己的 `codex-home`。**（同一类的 01、02、09 也一并修了。）

2. **第二层：修完 503，暴露出写入被拒。** 模型能回话了，但说「当前文件系统是只读」。可实验明明请求的是 `sandbox: "workspace-write"`。看内核返回的沙箱描述：

   ```json
   {"type":"workspaceWrite","writableRoots":[],"networkAccess":false}
   ```

   注意 `writableRoots` 是**空数组**——名义上是「可写工作区」，实际一个可写根都没有，于是等价于只读。模型于是绕过工具、打印一条命令让用户自己去终端敲。

3. **第三层（根因）：这台机器上 Windows 沙箱没配置。** 问内核沙箱就绪状态，得到 `notConfigured`。**修法是在 `codex-home/config.toml` 加一行：**

   ```toml
   [windows]
   sandbox = "elevated"
   ```

   加完同一个请求的响应变成 `workspaceWrite`，文件真的落盘了。

   **旁证很关键**：用官方安装的内核（`codex-cli 0.155.0-alpha.9.2`）在同样环境下跑同一个测试，`writableRoots` 同样是空的、同样写不进去。所以这不是自编译内核引入的问题，也不是探针改动引入的——**是环境缺配置，而且它把一个「写不进去」伪装成了「刹车坏了」**。

   顺带一条排查经验：`danger-full-access` 在这台机器上能写、`workspace-write` 不能，这个对比一下就把范围从「沙箱整体坏了」收窄到「可写根没生效」。

## 二、门槛类实验的常量会过期

修完之后全量回归，12 个绿，**09（上下文压缩）反而红了**：压缩次数 0。

原因不在压缩，在我自己上一轮的改动：把工具面收窄之后，开局上下文从 2 万出头掉到 9700 左右，几圈下来也才一万出头，而实验把压缩门槛写死在 15000 ——**门槛比实际能涨到的还高，自然永远撞不到**。

修法是把门槛调到 10500，改完立刻看到真实效果：活跃上下文 `10729 → 10171` 回落，压缩事件出现。

但这还没完，同一个实验后来又红了第二次，原因更有意思：**压缩的触发检查发生在每圈开始之前**。当时的上下文轨迹是 `9737 → 10267 → 10587`，而门槛 10500 卡在中间——第 3 圈开始检查时只有 10267，没够；等涨到 10587 时这一轮已经收尾了。门槛必须压到低于「第二圈结束时的上下文」才会在第 3 圈开始前真的踩到，于是又调到 10000。

**教训：门槛类实验的常量，要跟着被测系统的变化一起复查；而且要知道门槛是在哪个时刻被检查的。** 光调数值不够，还得对上检查发生的时点。否则红灯指向的是过期的假设，而不是真的缺陷——和上面那个坑是同一类。

## 三、双击启动：查了半天，坏的是我的测试方式

这一轮的教训跟前两个不一样：**报障是真的，根因却在测试手段本身。**

起因是想验一次真正的冷启动——把服务停掉、技能链接也删空，然后像用户那样双击 `启动 Agent Lab.bat`。结果：`launch.log` 是 0 字节、服务没起来、技能没重建。

**看起来就是启动器彻底坏了**，而且这是用户最常用的入口。于是往下查，中间套了好几层：

1. 先在隔离脚本里试：`node --version` 好使、COM 设工作目录好使、`where node` 能找到 —— 环境没问题。
2. 于是怀疑 `.bat`。实测那一句 `cd /d "C:\新建文件夹\agent-lab"`：

   ```
   文件名、目录名或卷标语法不正确
   ```

   **中文字符路径喂给 cmd，被 GBK 代码页转码搞坏了。** 而 `cd` 失败不会让批处理停下，所以后面的 `wscript` 照跑 —— 但真正的问题是，我一开始根本判断错了哪一层坏了。

3. 把 `cd` 去掉（改成让 `.vbs` 用 COM 自己设工作目录，走 Unicode 不经命令行），**从 bash 里再测，还是"失败"**。

4. 直到换成系统的方式来启动：

   ```powershell
   Start-Process -FilePath 'C:\新建文件夹\agent-lab\启动 Agent Lab.bat' -WindowStyle Hidden
   ```

   立刻成功：日志完整、技能从零重建、服务 ready。

**根因说清楚了**：启动器一直是好的。之前那几次"失败"，是我从 bash 里用 `cmd //c "启动 Agent Lab.bat"` 传**中文文件名**——同样被 GBK 转码搞坏，`cmd` 根本没找到这个 bat 文件，于是什么都没发生。**用户从资源管理器双击走的是 Unicode，不受影响。**

**两条收获**：

- 真问题确实有一个，值得修：`.bat` 里那句 `cd /d "%~dp0"` 在中文字符路径下会报错。它当时不致命（vbs 用的是自己算出的绝对路径），但它是噪音，而且只要将来有人给批处理加上「失败即中止」，就会真的坏掉。现在去掉了。
- 更要紧的是方法论：**测试手段本身会污染结论。** 我前面已经栽过一次（测试泄漏连接伪装成「拒绝失效」），这次是「用错的启动方式伪装成启动器坏了」。两次都是同一个形状——**先怀疑被测对象，而不是先怀疑自己怎么测的**。以后再遇到「一测就红」，尤其要盯住：这个测法跟用户的真实操作，差在哪一步。

## 四、同一轮里，同一个坑又踩了第二次

修完 `cd` 我以为好了，结果再测还是「服务起来了、窗口没有」。于是又往下查：枚举系统顶层窗口、看 Edge 进程、拆开启动器里 `openWindow` 的每一步 —— 全都正常，手工调 `openWindow` 甚至能把窗口开出来。

最后一次认真对比才发现：**问题还是我的起法**。我用 `(node start.mjs &)` 这种脱离 shell 的方式起进程，**会话一结束，整个进程树被连带清掉** —— 服务没了、Edge 子进程也没了。看起来就像「窗口从来没开过」。

换成能在会话之间存活的方式起，立刻正确：

```
服务  ready=true
窗口  visible | pid=38060 | Agent Lab
技能  从零自动重建
日志  launch.log 完整
```

**冷启动最终结论（全绿）**：把服务停掉、窗口关掉、技能链接删空、日志删掉，然后像用户那样双击 `启动 Agent Lab.bat`：

- `launch.log` 五条都在（含「已接入苍穹开发技能」）
- `codex-home/skills/` 里 `ok-cosmic` 和 `load-memory` 从零自动重建
- 服务 `ready=true`
- 顶层窗口真实存在：`Agent Lab`

值得记的是：**同一个「测试手段骗人」的坑，这一轮我踩了两次**。第一次是 bash 传中文文件名，第二次是脱离 shell 起进程，两次都很像真的产品故障。所以这条经验要写死：**在一个新环境里验证一个东西，先确认观测手段本身可信，再去怀疑被测对象。**

（副产品：为查这个问题写的窗口枚举脚本很有用——它按标题列出系统里所有顶层窗口。以后要确认「某个桌面窗口在不在」，这比肉眼截图可靠。用完删掉了，需要的话按这个思路重写十几行就有。）

## 五、改了「配置放哪」，要查一遍谁也在读它

这一轮把密钥从 `codex-home/config.toml` 挪进 `.env`（因为它要进版本库，明文密钥不该在里面）。改完 App 一切正常，实验 22 也全绿。

然后全量回归：**07、09、10 三个又红了**，报的还是「刹车没生效」「中断没生效」「没看到压缩」——跟密钥八竿子打不着。

真相是：这三个实验**直连内核、不走 App 桥**，所以它们读不到 `.env`，内核于是报：

```
Missing environment variable: `AGENT_LAB_API_KEY`.
```

一轮都跑不起来，脚本却各自报自己那件事失败。

**修法**：把读 `.env` 的逻辑抽成 `lib/env.mjs`，App 和所有直连内核的脚本共用同一份。受影响的一共五个：`01`、`02`、`07`、`09`、`10`、`11`、`16`。

**教训：把配置从一个地方挪到另一个地方时，要顺手查一遍「还有谁也在读它」。** 只改主路径（App）而漏掉旁路（实验脚本），就会留下一串看起来毫不相关的红灯——这是这一轮第二次遇到同形态的问题了。
